# FILE_STORAGE_ARCHITECTURE.md

Architecture decisions for Phase 5 (secure object storage, uploads, protected previews, file processing). See `MUTATION_ARCHITECTURE.md` for the Phase 4 mutation patterns this builds on, and `FILE_PROCESSING_RUNBOOK.md` for hands-on local operation.

## Original/preview separation

Every file lives as up to two separate storage objects, never one:

- **Original** (`originals/`) — the exact bytes the creator uploaded, privately stored, never modified, never served to a client review portal in this phase.
- **Preview** (`previews/`) — a smaller, watermarked, metadata-stripped derivative generated by the worker (images only — see "Supported file types"). Never the same object as the original; never the same storage key.

A third prefix, `temp/`, holds objects mid-upload before server-side verification — see "Upload-session lifecycle." Nothing is ever served directly from `temp/`.

All three prefixes live inside **one bucket** (`S3_BUCKET`, default `project-vault-files`), not three separate buckets — simpler to provision and lock down (one bucket policy, "no public access," to reason about), while the prefixes still give the storage keys a clear, greppable structure for auditing.

## Storage-key rules

- Every key is `{prefix}/{48-hex-char-random-string}{.extension}` (`src/storage/storage-keys.ts`), generated with `node:crypto`'s `randomBytes(24)` — 192 bits of entropy, not a database id, not a hash of the filename, not anything guessable or enumerable.
- **A storage key is never derived solely from a database id.** `WorkspaceFile`/`FileVersion` ids are sequential-ish cuids used for database relations only; the storage key that actually locates bytes in the bucket is always the independent random string above. Even if an attacker enumerated every `WorkspaceFile` id, they couldn't derive a single object's storage key from it.
- **A temp upload's key is never reused as its permanent key.** On successful verification, `completeUploadSession` generates a **brand-new** `originals/` key and copies the object there, then deletes the `temp/` object. This means even if a temp key were somehow guessed or leaked during the upload window, it stops being valid the moment the upload completes.
- Storage keys are **never** sent to the browser except as part of a presigned URL's query string (which itself expires) — see "Presigned URL rules." No API response, React prop, HTML attribute, or log line ever contains a raw key. The UI only ever knows opaque database ids (`WorkspaceFile.id`).

## Upload-session lifecycle

`UploadSession` (Prisma model) tracks one presigned-upload attempt from request to resolution:

1. **Requested** (`createUploadSession`, `src/data-access/uploads.ts`) — verifies workspace ownership, validates the *declared* filename/MIME type/size against `src/storage/storage-config.ts`'s limits, generates a random `temp/` key, and creates the `UploadSession` row (`status: PENDING`, `expiresAt: now + UPLOAD_SESSION_EXPIRY_SECONDS`).
2. **Uploading** — the browser PUTs directly to the presigned URL (`XMLHttpRequest`, for real progress events — see `src/hooks/use-file-upload-queue.ts`). The server is not in this path at all; MinIO/S3 receives the bytes directly.
3. **Completed or expired** (`completeUploadSession`) — see "File validation" below for what "completed" actually verifies. A session can only be completed once (`status` transitions `PENDING → COMPLETED`, checked and enforced) and only before `expiresAt` (`PENDING → EXPIRED` otherwise, which also disqualifies it from ever completing).
4. **Never reused.** A `storageKey` is `@unique` in the schema — even if a client replayed an old presigned URL after its session already completed or expired, there's no code path that reissues a completion against the same session or generates a fresh presigned URL for an already-used key.

No signed URL is ever written to Postgres — `UploadSession.storageKey` is the object's *location*, not a URL; the actual presigned URL is generated on demand (`src/storage/signed-urls.ts`) and handed to the browser exactly once, in the HTTP response.

## Ownership authorization

Every storage-touching operation resolves the authenticated creator via `requireAuthenticatedUser()`/`requireOwnedWorkspace()`/`requireOwnedWorkspaceFile()` (`src/data-access/authorization.ts`, extended in this phase with `requireOwnedWorkspaceFile`, which resolves ownership through the file's parent workspace — never a client-supplied `workspaceId`). This mirrors Phase 4's `OwnershipError` pattern: a missing file and a not-owned file both throw the same generic error, both routes/actions treat them identically (404/"not found"), so a caller can never distinguish "doesn't exist" from "belongs to someone else."

`creatorId` is never accepted as upload-session/file-action input — always derived from the session, exactly like every Phase 4 mutation.

## Presigned URL rules

| URL kind | Expiry | Scope | Reusable? |
|---|---|---|---|
| Upload PUT URL | `UPLOAD_SESSION_EXPIRY_SECONDS` (default 900s / 15 min) | One specific `temp/` key, one declared `Content-Type` (signed into the URL — a mismatched header fails the S3 signature check) | No — the session it belongs to can only be completed once |
| Preview GET URL | 60 seconds (hardcoded in `src/storage/signed-urls.ts`, deliberately not configurable to something long) | One specific `previews/` key | Yes within its 60s window, but a fresh one is generated on every "View Protected Preview" click — the UI never caches or reuses one |

No original file ever gets a presigned URL issued to any creator-facing code path in this phase — `getOwnedFilePreviewUrl` (`src/data-access/files.ts`) only ever resolves `currentVersion.previewStorageKey`, and there is no equivalent function for `originalStorageKey`. This is a structural guarantee, not just a convention: the only function capable of presigning a GET (`s3StorageProvider.createPresignedDownloadUrl`) is called from exactly one call site in application code, and that call site is hardcoded to the preview key.

Content-length restriction on the upload PUT is **best-effort, not fully enforced by the presigned URL itself** — S3-compatible presigned PUT URLs sign the `Content-Type` header but not `Content-Length` in the SDK configuration used here. The actual, authoritative size check happens server-side after upload, via `headObject` (see "File validation").

## File validation

Server-side verification (`completeUploadSession`) never trusts:

- **Browser-declared size** — re-checked via `s3StorageProvider.headObject()` against the *actual* object in storage; any mismatch (even 1 byte) is rejected (`UploadVerificationError`) and the temp object is deleted.
- **Browser-declared MIME type** — the object is downloaded and passed through `file-type`'s magic-byte sniffing (`fileTypeFromBuffer`), not trusted from the `Content-Type` the browser sent. Only a sniffed type in the MVP allow-list (`src/lib/file-kind.ts`) is accepted; everything else — including a file that merely *claims* to be a JPEG — is rejected and the temp object deleted.
- **Original filename** — sanitized (`src/lib/filename-sanitize.ts`: strips path components, replaces unsafe characters, caps length) before ever being stored as `WorkspaceFile.displayName`, and never used to build a storage key.
- **A frontend "upload complete" signal** — the browser's XHR success only tells the client to *ask* the server to verify and complete; nothing is created in the database until the server has independently confirmed the object exists with the right size and content.

### Supported file types (MVP)

| Kind | MIME types | Preview | Notes |
|---|---|---|---|
| Image | `image/jpeg`, `image/png`, `image/webp` | Real, watermarked | See "Watermark generation" |
| PDF | `application/pdf` | None — "locked deliverable" | Stored privately; UI shows filename/size/locked status and an honest "Preview not available in this MVP" message |
| Archive | `application/zip`, `application/x-zip-compressed` | None — "locked deliverable" | Same as PDF |

Explicitly, permanently rejected regardless of extension: HTML, XHTML, SVG (can embed `<script>`), JavaScript, and common executable MIME types (`src/lib/file-kind.ts`'s `EXPLICITLY_REJECTED_MIME_TYPES`) — this list is checked *in addition to* the allow-list, so it can never accidentally be bypassed by a future allow-list edit.

Password-protected archives are **not detected** in this phase — ZIP validation here is limited to magic-byte type sniffing, not structural inspection. Documented as a known gap in "Security limitations" below.

### Image-specific validation

- **Decoded, not just sniffed.** `src/lib/image-preview.ts`'s `generateWatermarkedPreview` calls Sharp's `.metadata()`, which fails loudly (`UnsupportedImageError`) on a malformed image, before any resize/composite work happens.
- **Pixel-dimension limit** (`PREVIEW_MAX_INPUT_DIMENSION_PX`, default 8000px on either axis) is checked against the metadata **before** any decode-heavy operation runs — the primary decompression-bomb defense: an image whose *declared* dimensions exceed the limit is rejected without ever asking libvips to actually decode/resize pixel data at that scale.
- **Checksums** (`src/lib/checksum.ts`, SHA-256) are computed for both the original and the generated preview and stored on `FileVersion` — verifiably different, since the preview is a distinct, watermarked, re-encoded, metadata-stripped image (see `src/lib/image-preview.test.ts` for a direct assertion of this).

## Watermark generation

`src/lib/watermark.ts` (pure, no image decoding) + `src/lib/image-preview.ts` (Sharp-dependent):

- **Content:** "PREVIEW ONLY — Project Vault", the client's name and email, and the workspace title (`buildWatermarkLines`) — tiled diagonally across the whole preview (`buildWatermarkSvg`), not a single corner stamp, per the brief's "not presented as impossible to remove" framing: it's a visible deterrent against casual reuse, not a cryptographic protection.
- **XML/SVG escaping is mandatory, not optional.** `escapeXmlText` runs on every one of the three text lines before they're interpolated into the generated SVG string — client name, client email, and workspace title are all creator/client-controlled text that could otherwise contain `<`, `>`, `&`, quotes, or a literal `</text><script>...` injection attempt. The SVG itself is otherwise built entirely from this app's own template strings; **no client-supplied SVG or HTML is ever rendered** — see `src/lib/watermark.test.ts` for a direct injection-attempt test.
- **Centralized configuration** (`getWatermarkConfig()`): font size, opacity (0.28 — visible but not defacing), rotation angle, and tile spacing are defined in exactly one place, so the visual treatment can't drift between call sites (there is only one call site).
- **Metadata stripped, orientation corrected.** Sharp's `.rotate()` with no arguments auto-orients using the EXIF orientation tag; because `withMetadata()` is never called afterward, Sharp's own default behavior strips every other metadata field (EXIF, GPS, ICC, XMP) from the output. This is the entire mechanism — no separate "strip metadata" step exists because none is needed once `withMetadata()` is simply never invoked.
- **Original files are never touched.** `generateWatermarkedPreview` only ever reads the original buffer; every output (resized, composited, re-encoded) is written to a new buffer and a new `previews/` storage key. There is no code path that overwrites or mutates an `originals/` object after creation.
- **Limits, all centrally configured** (`src/storage/storage-config.ts`'s `getPreviewLimits()`): max input dimension (decompression-bomb defense), max output dimension (preview stays meaningfully smaller than the original), processing timeout (`sharp().timeout()`), and JPEG quality. Worker retry attempts are governed separately (`getWorkerConfig().maxAttempts`).

## Database models

Added in migration `20260728085350_phase5_file_storage` (see `DATABASE_SETUP.md` for the hands-on note):

- **`WorkspaceFile`** — one row per logical file. `currentVersionId` is the single, explicitly-set pointer to "the version currently shown" — never inferred by picking "whichever version row is newest," so a half-processed new version (future re-upload support) could never briefly become what the UI resolves. Soft-deletable (`deletedAt`).
- **`FileVersion`** — `originalStorageKey`/`previewStorageKey` (both `@unique`), both checksums, both sizes (`BigInt`), dimensions, and a safe `processingError` summary. `@@unique([fileId, versionNumber])` — versions are ordered and unambiguous per file.
- **`FileProcessingJob`** — one row per processing *attempt*. `attempts` is the attempt number **this row represents** (set explicitly at creation — `1` for the first attempt from `completeUploadSession`, `previousAttempts + 1` for a creator-triggered retry), not a counter mutated in place; this is what `canRetry`/the retry-limit check compares against `FILE_WORKER_MAX_ATTEMPTS`.
- **`UploadSession`** — see "Upload-session lifecycle" above.
- Money-style care applied to sizes too: every `sizeBytes`/`originalSizeBytes`/`previewSizeBytes`/`expectedSizeBytes` column is `BigInt`, never `Int` (which could silently overflow) and never `Float`. `src/lib/bytes.ts`'s `bigIntToDisplayNumber`/`numberToStorageBigInt` are the only two conversion points between BigInt and plain `number`, and the former throws rather than silently losing precision if a value ever exceeded `Number.MAX_SAFE_INTEGER` (it never does in practice, but the guard exists so a future bug fails loudly instead of corrupting a displayed size).

## Deletion behavior

`deleteOwnedFile` (`src/data-access/files.ts`):

1. Ownership + status check (`FileNotDeletableError` for a financially-locked workspace — `PAID`/`FILES_UNLOCKED`/`DELIVERED` — same `FINANCIAL_LOCK_STATUSES` list Phase 4 already established for workspace edits).
2. **Soft-delete first, in a transaction with the activity log entry** — `WorkspaceFile.status → DELETED`, `deletedAt` set. This is the *authoritative* "is this file gone" signal; every read (`getWorkspaceFiles`) already filters `deletedAt: null`.
3. **Storage cleanup is best-effort, after the database commit, via `Promise.allSettled`** — a failed object deletion (network blip, storage temporarily unavailable) is logged (`console.error`) but never rolls back or blocks the mutation. The file is already gone from every UI a creator can see; a stray object in `originals/`/`previews/` is a cleanup concern, not a data-integrity or security one (it's still private — nothing points at it, and nothing ever will again).

This matches the Phase 5 brief's explicit instruction to "handle partial object-deletion failure safely" — the alternative (making deletion an all-or-nothing operation spanning both the database and two S3 calls) would mean a transient storage hiccup could leave a creator unable to remove a file they're entitled to remove.

## Security limitations

Explicitly **not** implemented in this phase — do not assume any of these are covered:

- **No antivirus/malware scanning.** Uploaded files are validated for type/size/dimensions only. A file that is a structurally-valid JPEG/PNG/WebP/PDF/ZIP but also contains embedded malicious content (e.g., a booby-trapped PDF, a ZIP bomb with a valid-looking small outer size) is not scanned. This app is never described as "malware-scanned" anywhere in its UI or documentation.
- **No password-protected-archive detection.** ZIP validation is magic-byte-only.
- **Content-Length is not cryptographically enforced on the presigned upload URL** — enforced after the fact via `headObject`, not preventable at upload time. A creator could theoretically upload more bytes than declared to `temp/`; the completion step would simply reject it (size mismatch) and it's deleted, so this cannot result in an accepted, oversized file — only a slightly wasted (and cleaned-up) temp-storage write.
- **No rate limiting** on upload-session creation — a malicious authenticated creator could create many sessions in quick succession. The per-workspace file-count and total-size limits bound the *accepted* damage, but not the request volume itself.
- **No client-facing access of any kind.** Previews are creator-only in this phase — there is no secure client-review-token authorization yet (deferred to a later phase, per the brief).
- **No video preview processing, no PDF visual preview** — deliberately out of scope; PDF/ZIP are locked deliverables with no visual preview at all in this MVP.
