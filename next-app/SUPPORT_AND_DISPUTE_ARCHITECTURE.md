# Support & Dispute Architecture (Phase 7.5)

Minimal support-ticket workflow — `src/data-access/support-tickets.ts`,
`src/validation/support-ticket.ts`, `src/actions/support-tickets.ts`.

## Models

`SupportTicket` (`ticketNumber` unique, e.g. `TCK-M5X2A9B3`, generated by
`generateTicketNumber()` with a retry-on-collision guard — see
`createTicketWithUniqueNumber`) and `SupportTicketMessage`, both in
`prisma/schema.prisma`. Categories: `PAYMENT` / `DELIVERY` /
`QUALITY_DISPUTE` / `FILE_PROCESSING` / `ACCOUNT` / `OTHER`. Statuses:
`OPEN` / `UNDER_REVIEW` / `WAITING_FOR_CREATOR` / `WAITING_FOR_CLIENT` /
`RESOLVED` / `CLOSED`.

## Creator flow

- `/support` — list of every ticket the creator owns (`getOwnedSupportTickets`).
- `/support/new` (optionally `?workspaceId=...`, linked from the "Raise
  Support Ticket" button on the workspace detail page) — create
  (`createCreatorSupportTicket`), ownership of `workspaceId` re-verified
  server-side via `requireOwnedWorkspace`, never trusted from the query
  string.
- `/support/[id]` — thread + reply (`addCreatorSupportMessage`, which also
  flips the ticket to `WAITING_FOR_CLIENT`).

## Client flow

- `ClientSupportModal` inside the master review portal — list, create, and
  reply, all scoped through the already-authorized `ReviewContext`.
- `createClientSupportTicket(context, input)` always sets `workspaceId` and
  `creatorId` from `context`, never from client input — a client cannot
  target a different workspace's ticket even by tampering with a form
  field, because there is no form field for it.
- `getClientSupportTickets(context)` filters strictly by
  `workspaceId: context.workspaceId` — this is the access boundary. A
  client reaching the review portal for workspace A can never see, list,
  or reply to a ticket raised on workspace B, even one belonging to the
  same creator. Verified end-to-end in
  `src/data-access/support-tickets.integration.test.ts`.
- `reviewLinkId` is recorded on the ticket for traceability but is never
  itself the authorization check — `workspaceId` is.

## Admin flow

`/admin/support` (paginated list) and `/admin/support/[ticketId]` (detail +
reply + status change) — `requireAdminRole`, re-verified inside every
`src/data-access/support-tickets.ts` admin function independently of the
route layout.

**The only two writes an admin can make anywhere in the system** are
`addAdminSupportMessage` and `updateSupportTicketStatus`. Neither touches
`Payment`, `DownloadGrant`, `ReviewComment`, `WorkspaceApproval`, or
`Workspace` in any way — there is no function an admin can call that would
let them mark a payment captured, fabricate a Razorpay payment, unlock
files without a valid payment/release, rewrite a comment, delete audit
history, or change the approved file snapshot. This is enforced by absence
(no such function exists in `src/data-access/admin.ts` or
`support-tickets.ts`), not by a permission check that could be
misconfigured — see `support-tickets.integration.test.ts`'s admin test,
which asserts the workspace's status/deliveryMode are untouched after an
admin reply + status change.

## Audit trail

Every create/reply/status-change writes a `SUPPORT_TICKET_*` activity
entry (`src/lib/activity-log.ts`) with `ticketNumber` in its metadata —
never the ticket body itself, to keep activity-log rows short and never a
place sensitive dispute content could leak into an unrelated view.

## Deferred

- No email notifications when a ticket receives a reply.
- No SLA timers or escalation.
- No file attachments on a ticket message.
